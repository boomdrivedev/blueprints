Timber · architecture

One shape, three deployments

Every owner of timber runs the same five steps in the same order and keeps the same two records. Boomdrive Cloud carries the news from one step to the next in every deployment, down to a single host, and on each host the runner launches the job that runs the command. Deployments differ in two things only: which machine runs each step, and who holds which key. The statement beside this page holds the clauses, and its models hold the plans.

The shape

Built once

Publish offers the bytes the checks built. It never builds them again, so what passed is what runs.

Offering is not accepting

Two keys. No machine that builds holds the accepting key, except one host that is the whole deployment and says so in its claim.

The owner keeps everything

The store, the ledger and the policy are the owner's in every deployment. Moving between deployments changes a host's bindings file.

1. One host

A developer's laptop, or the fleet's deneb, under Boomdrive Cloud. Timber needs no setup here: with no bindings file it uses a store on disk, a key it makes on first use and a ledger beside the branch.

2. A team

A few people and a few hosts under Boomdrive Cloud. Checks leave the publishing host, so the store becomes a shared registry and the gate moves to a host no check can reach.

3. An enterprise under a control plane

Boomdrive Cloud, a build fleet in the owner's cloud account, and a product with a control plane of its own that deploys to many installs. Switchboard is the worked case.

Where GitHub Actions fits

Boomdrive Cloud cannot start anything inside a GitHub Actions job. It reaches timber only through a runner, a runner dials out, and a job has none. So Actions takes the step that needs no starting from the cloud, and the rest stays on a host.

A registry is needed as soon as one check runs off the publishing host, since that is how its builds reach the publish.

Timber without Boomdrive

Timber also stands alone, which is how someone adopts it before Boomdrive. A person's shell, or a forge's workflow on the push to main, runs the same commands, and the store, the ledger and the policy stay as they are. Sluice and Boomdrive release from such a workflow today. It is a way in, not one of the plan's deployments.

The fleet, end to end

A change to flume, followed to the fleet's machines. Every repository runs the same three steps: a landing, timber publish, timber apply. Boomdrive Cloud launches each on deneb's runner, nothing runs in GitHub Actions, and versions and builds live in GHCR.

The family's store is GHCR

Under the boomdrivedev organization: public for the tools, private packages for swancloud. The user, 2026-11-16. Timber's registry store is designed for GHCR and not proven.

The checks build the release commit

A landing that makes a version is checked as its release commit, so the published binary says its version and is the build the checks ran. Two queued landings never claim one version. Timber record 0037.
